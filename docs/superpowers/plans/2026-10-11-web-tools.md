# Web Tools Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the agent two local web tools: `web_fetch`, which retrieves a URL and converts an
HTML response to plain text unless the model asks for the raw body, and `web_search`, which
returns ranked results through the Brave Search API when a key is configured and through
DuckDuckGo's HTML endpoint otherwise. The DuckDuckGo fallback was later replaced by six real search
APIs — see `2026-10-12-web-search-providers.md`.

**Architecture:** A new `internal/web` package owns the HTTP client, a stdlib-only HTML tokenizer
with a text converter built on it, and the two search backends. `internal/tools/web.go` exposes
them as built-in tools with the same argument validation, output cap, and presentation conventions
as the other tools, and reads its policy from `web.*` settings plus the `no_web` switch.

**Tech Stack:** Go standard library (`net/http`, `net/url`, `mime`, `encoding/json`, `crypto`
nothing — no new modules), the existing tool registry and config store.

**Spec:** the C implementation ships no web tools (`src/tools/` is bash, edit, read, task_wait, write), so
this is a deliberate gax addition like the built-in `customize-gax` skill. The keyless fallback
follows what other terminal agents do: DuckDuckGo's `html.duckduckgo.com` endpoint needed no API
key, and its markup was verified against the live service before writing the parser — the endpoint
was removed again in `2026-10-12-web-search-providers.md` once it throttled and challenged scripted
clients in practice.

## Constraints

- Standard library only; `go.mod` keeps no `require` block.
- HTML conversion is lenient: malformed markup, stray `<`, and unclosed tags degrade to text
  instead of failing, and script/style content never leaks into the output.
- `strip: false` returns the raw body (still capped and charset-decoded), so a caller can read
  markup, JSON, XML, or CSV.
- Non-text responses are reported by media type and size, never dumped into the conversation.
- Both tools respect `tool_output_cap` for what the model sees and `web.max_bytes` for what is
  downloaded; `web.timeout` bounds one request, and cancellation from the turn reaches the request.
- `no_web` removes both tools from the advertised set and refuses a stale call to one.
- The Brave key never appears in tool output or diagnostics; a rejected key names the variable and
  the fallback instead of echoing the value.
- A search that returns nothing usable is an error with the reason (throttled, challenged, empty),
  never a silent empty list.

## Record

- DuckDuckGo's HTML endpoint answers a scripted client with HTTP 202 and an anomaly page; it serves
  the result list with a browser User-Agent **and** an HTML Accept header. The backend therefore
  requires 200 and reports any other status as an error, because a challenged search looks like a
  successful empty page otherwise. (In practice the endpoint throttled often enough that it was
  replaced by real search APIs; see `2026-10-12-web-search-providers.md`.)
- The converter is a hand-rolled tokenizer rather than regexes: `<script>`/`<style>`/`<title>` are
  scanned as raw text so a `<` inside them cannot open a tag, attributes may contain `>`, and
  unknown entities survive verbatim.
- Brave snippets and titles carry `<strong>` markup; both search backends run their text fields
  through the same converter, so results are plain text regardless of backend.
- Rendering: a fetched document is the body, a blank line, then
  `[200 OK · text/html · stripped · 1.2K]`, adding `redirected to <url>` when redirects moved the
  request and `first <size> of a larger response` when the byte limit cut it. Search results are
  numbered entries (title, URL, snippet) followed by `[3 results · brave]`.
- The tools are appended after `task_wait` in the advertised list, so an existing conversation's
  earlier tool block stays a prefix of the new one.
- Neither tool grants reach the agent did not already have — `bash` runs `curl` against the same
  network — they exist so reading a page does not need shell quoting, an HTML parser, and a byte
  cap written by the model on every call.

## gax additions

The web tools are gax's own: nothing here has a counterpart in the C implementation, so the tool
names, descriptions, and rendering are designed here. Everything adjacent stays aligned with the
ported code — the tools use the same registry, output-cap, and presentation plumbing, and `no_web`
follows the `no_tasks` shape.
